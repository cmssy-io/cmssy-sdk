# Migrating from v14 to v15

v15 finishes the vocabulary cleanup CMS-1709 started on the backend: the place
a layout block renders is a **region**, everywhere. v14 mixed two words for the
same concept - `defineBlock({ layoutPositions })` next to
`defineCmssyLayout({ regions })`, `CmssyLayoutSlot position=` next to
`CmssyRegion<typeof layout>`. v15 uses one.

## Run the codemod

```bash
npx @cmssy/codemod v15 ./
```

It rewrites `layoutPositions` to `layoutRegions` and `position=` to `region=`
on `CmssyLayoutSlot`, `CmssyServerLayout`, `CmssyEditableLayout` and
`CmssyLazyLayout`. Review the diff, then fix the remaining renames below by
hand (they are option and field names the codemod does not touch). Two known
limits: `layoutPositions` is rewritten even inside string literals and
comments, and a slot component nested inside another slot's prop expression
keeps its `position=` - both are visible in the diff you review.

## What changed

| v14                                                                                           | v15                                                     |
| --------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| `defineBlock({ layoutPositions: [...] })`                                                     | `defineBlock({ layoutRegions: [...] })`                 |
| `CmssyLayoutSlot position="header"`                                                           | `CmssyLayoutSlot region="header"`                       |
| `CmssyServerLayout position=` / `CmssyEditableLayout position=` / `CmssyLazyLayout position=` | `region=`                                               |
| `resolveCmssyLayout(cmssy, { position })`                                                     | `resolveCmssyLayout(cmssy, { region })`                 |
| `resolveEditorLayoutBlockData({ position })`                                                  | `resolveEditorLayoutBlockData({ region })`              |
| `CmssyLayoutGroup.position`                                                                   | `CmssyLayoutGroup.region`                               |
| `loadCmssyPage` / `createCmssyLoader` `positions` option (astro, remix)                       | `regions`                                               |
| `LayoutPosition` (type, from `@cmssy/types`)                                                  | `LayoutRegionId`                                        |
| `TemplateLayoutPosition` / `TemplateConfig.layoutPositions`                                   | `TemplateLayoutRegion` / `TemplateConfig.layoutRegions` |
| `data-layout-position` DOM attribute                                                          | `data-layout-region`                                    |
| bridge messages: `layoutPosition` key on `cmssy:ready` blocks, `cmssy:click`, `cmssy:patch`   | `layoutRegion`                                          |
| manifest push: per-block `layoutPositions` key                                                | `layoutRegions`                                         |

## The API moved with the backend

The GraphQL surface renamed in the same release - `LayoutBlock.region`,
`ResolvedLayout.region`, `Page.layoutRegionSettings`,
`page.updateLayoutRegionSettings`. v15 speaks the new surface; v14 speaks the
old one. Upgrade the SDK and deploy against a backend that already serves the
renamed schema - the two are released in lockstep, so npm's latest SDK always
matches the live API.

## Why a major

Every rename above is breaking for the block manifest your site pushes, the
bridge protocol the editor speaks, and the delivery query shape. There is no
compatibility shim: cmssy migrates data up front instead of supporting two
vocabularies (the admin editor, MCP tools and delivery API all renamed in the
same release).
