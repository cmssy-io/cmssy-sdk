# v12 → v13

The places a layout block can live stop being a fixed list of six and become something your site declares.

## What changed

`@cmssy/core` and `@cmssy/react` no longer export `layoutRegionValues`, and `LayoutRegionId` is now `string` rather than the union `"top" | "header" | "sidebar_left" | "sidebar_right" | "footer" | "bottom"`. In their place:

```ts
// cmssy.config.ts
import { defineCmssyConfig, defineCmssyLayout } from "@cmssy/next";

export const layout = defineCmssyLayout({
  regions: [
    { id: "header", label: "Header" },
    { id: "footer", label: "Footer" },
  ],
});

export const cmssy = defineCmssyConfig({
  org: process.env.CMSSY_ORG_SLUG,
  workspaceSlug: process.env.CMSSY_WORKSPACE_SLUG,
  draftSecret: process.env.CMSSY_DRAFT_SECRET,
  layout,
});
```

`CmssyRegion<typeof layout>` is the union of the ids you declared. `CmssyLayoutSlot`'s `position` is typed to `config.layout`, so a slot for a region you did not declare no longer compiles. The edit page tells the editor which regions exist - `createCmssyPage` does it for Next on its own; on Astro and React Router the page result / loader data now carries `layoutRegions`, which you pass to `CmssyEditor` as `edit={{ editorOrigin, layoutRegions }}`.

Ids start with a letter or digit and continue with lowercase `[a-z0-9_-]`, at most 50 characters, at most 20 regions, no duplicates; a label is at most 100 characters. `defineCmssyLayout` throws on anything else the moment `cmssy.config.ts` is evaluated, so a bad id never reaches the editor. Write the `regions` array inline (or `as const`) - ids read from a plain variable widen to `string`, and the narrowing is gone.

`defineCmssyLayout` uses a `const` type parameter, so the published declaration files need **TypeScript 5.0 or newer** in your project.

## Why

The six positions were cmssy's guess at every site's page. A site with a cookie bar, a promo strip and no sidebar had to shoehorn them into `top` and `sidebar_left`, and the editor listed four regions the site never rendered - content an editor could fill and a visitor would never see. Now the site says what it has, the editor shows exactly that, and the compiler holds the slot to the same list.

## What you change

1. Add `defineCmssyLayout` to `cmssy.config.ts` as above, listing the regions your routes actually mount. A site that skips this keeps working: the editor falls back to `header` and `footer`.
2. Replace any `LayoutRegionId` or `layoutRegionValues` in your own code:

```diff
-import { layoutRegionValues, type LayoutRegionId } from "@cmssy/react";
+import type { CmssyRegion } from "@cmssy/react";
+import type { layout } from "@/cmssy.config";
-const slot = (position: LayoutRegionId) => ...
+const slot = (position: CmssyRegion<typeof layout>) => ...
-for (const position of layoutRegionValues) ...
+for (const { id } of layout.regions) ...
```

`import type { layout }` is erased at build time, so a `"use client"` component may use `typeof layout` without dragging the config into the browser.

3. Astro and React Router edit pages: pass `layoutRegions` through to `CmssyEditor`:

```diff
-const { page, layouts, locale, defaultLocale, enabledLocales, editorData } =
+const { page, layouts, locale, defaultLocale, enabledLocales, editorData, layoutRegions } =
   await loadCmssyPage(cmssy, Astro.request, Astro.url, { blocks });
 ...
-<CmssyEditor ... edit={{ editorOrigin }} />
+<CmssyEditor ... edit={{ editorOrigin, layoutRegions }} />
```

A site that already renders a region outside the old six - say `promo` - declares it and it appears in the editor the next time the edit page loads. Blocks the editor had placed in a position you no longer declare stay stored and are shown under Layouts with a notice until you move or delete them.

Requires `@cmssy/types@0.37.0`; the packages pin it, so `pnpm update @cmssy/next` (or whichever adapter you use) brings it along.
